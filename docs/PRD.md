# 커피 주문 앱

## 1. 프로젝트 개요

### 1.1 프로젝트명
COZY 커피 주문 앱

### 1.2 프로젝트 목적
사용자가 커피 메뉴를 주문하고, 관리자가 주문을 관리할 수 있는 간단한 풀스택 웹 앱

### 1.3 개발 범위
- 주문하기 화면(메뉴 선택 및 장바구니 기능)
- 관리자 화면(재고 관리 및 주문 상태 관리)
- 데이터를 생성/조회/수정/삭제할 수 있는 기능

### 1.4 이번 문서의 범위
이 문서는 주문하기·관리자 화면의 프런트엔드 요구사항과 백엔드 API·데이터 모델 요구사항을 정의한다.

## 2. 기술 스택
- 프런트엔드: HTML, CSS, 리액트, 자바스크립트
- 백엔드: Node.js, Express
- 데이터베이스: PostgreSQL

## 3. 기본 사항
- 프런트엔드와 백엔드를 따로 개발
- 기본적인 웹 기술만 사용
- 학습 목적이므로 사용자 인증이나 결제 기능은 제외
- 메뉴는 커피 메뉴만 있음

## 4. 주문하기 화면 PRD

### 4.1 목표 및 사용자
- 사용자가 커피 메뉴와 추가 옵션을 선택해 장바구니에 담고, 주문을 제출할 수 있어야 한다.
- 대상 사용자는 별도 가입이나 로그인 없이 커피를 주문하려는 방문자다.
- 결제는 앱에서 처리하지 않는다. 주문 제출은 주문 정보를 앱에 등록하는 단계다.

### 4.2 화면 구성
1. **상단 내비게이션**
   - 브랜드명 `COZY`를 표시한다.
   - `주문하기`와 `관리자` 메뉴를 제공한다.
   - `주문하기`는 현재 화면임을 시각적으로 표시하고, `관리자`는 관리자 화면으로 이동한다.
2. **메뉴 목록**
   - 메뉴를 카드 형태로 표시한다. 각 카드에는 메뉴 이미지, 메뉴명, 기본 가격, 짧은 설명, 추가 옵션, `담기` 버튼이 포함된다.
   - 와이어프레임 예시 메뉴는 아메리카노(ICE) 4,000원, 아메리카노(HOT) 4,000원, 카페라떼 5,000원이다. 실제 메뉴와 가격은 관리되는 메뉴 데이터를 기준으로 표시한다.
   - 옵션은 메뉴별로 설정한다. 와이어프레임의 예시는 샷 추가(+500원), 시럽 추가(+0원)이며, 선택 옵션과 추가 금액을 함께 표시한다.
3. **장바구니**
   - 담긴 각 메뉴의 메뉴명, 선택 옵션, 수량, 항목 금액을 표시한다.
   - 장바구니 전체 금액을 표시하고, `주문하기` 버튼을 제공한다.
   - 항목 금액은 해당 메뉴의 기본 가격과 선택 옵션 금액을 합한 단가에 수량을 곱해 계산한다. 전체 금액은 모든 항목 금액의 합이다.
   - 빈 장바구니에는 빈 상태 안내를 표시하고, 주문 제출을 할 수 없도록 한다.

### 4.3 사용자 흐름 및 동작
1. 사용자가 메뉴 카드에서 필요한 옵션을 선택한다.
2. `담기`를 누르면 선택한 메뉴와 옵션이 장바구니에 추가되고, 장바구니와 총액이 갱신된다.
3. 동일한 메뉴와 동일한 옵션 조합을 다시 담으면 한 항목으로 합산하고 수량을 늘린다. 옵션 조합이 다르면 별도 항목으로 표시한다.
4. 사용자가 장바구니의 `주문하기`를 누르면 장바구니 내용을 주문으로 제출한다.
5. 주문이 성공하면 성공 안내를 표시하고 제출한 장바구니를 비운다. 제출에 실패하면 오류 안내를 표시하고 장바구니를 유지해 재시도할 수 있게 한다.

### 4.4 기능 요구사항
- **메뉴 표시:** 판매 가능한 커피 메뉴와 가격 및 옵션을 표시한다. 이미지나 설명이 없는 경우에도 메뉴명과 가격은 확인할 수 있어야 한다.
- **옵션 선택:** 각 메뉴의 옵션은 선택 여부를 명확하게 표현한다. 선택하지 않은 옵션은 금액에 포함하지 않는다.
- **장바구니 추가:** 메뉴를 장바구니에 담은 직후 장바구니 항목, 수량, 금액이 최신 상태로 표시되어야 한다.
- **금액 계산:** 메뉴 단가와 옵션 금액을 기준으로 항목 금액 및 총액을 계산하며, 화면의 모든 금액은 원 단위로 표시한다.
- **주문 제출:** 장바구니가 비어 있지 않을 때 주문 제출을 허용한다. 제출 중에는 중복 제출을 방지하고 진행 상태를 표시한다.
- **결과 안내:** 주문 성공과 실패를 사용자가 알아볼 수 있게 안내한다. 오류 시 기존 장바구니 항목과 선택 내용은 보존한다.
- **화면 이동:** 상단 내비게이션에서 주문하기 화면과 관리자 화면으로 이동할 수 있다.

### 4.5 예외 및 상태
- 메뉴를 불러오는 동안 로딩 상태를 표시하고, 불러오기에 실패하면 오류와 다시 시도할 방법을 제공한다.
- 메뉴가 없으면 메뉴가 없다는 안내를 표시한다.
- 주문 제출에 실패해도 장바구니를 초기화하지 않는다.
- 옵션이나 메뉴 데이터가 변경되어 제출 시 가격/판매 가능 상태가 유효하지 않다면 주문을 제출하지 않고 사용자에게 다시 확인하도록 안내한다.

### 4.6 레이아웃 및 접근성
- 데스크톱에서는 메뉴 카드를 여러 열로 배치하고 장바구니를 메뉴 목록 아래에 표시한다. 와이어프레임은 메뉴 카드 3개 열을 예시로 한다.
- 화면 폭이 좁아지면 카드 열 수를 줄여 가로 스크롤 없이 읽고 조작할 수 있게 한다.
- 버튼, 체크박스, 내비게이션은 키보드로 조작할 수 있고, 각 입력에는 메뉴명과 옵션 등 식별 가능한 이름을 제공한다.
- 옵션 가격과 총액은 색상만으로 구분하지 않고 텍스트로도 명확히 표시한다.

### 4.7 인수 기준
- 메뉴 카드에서 옵션을 선택하고 `담기`를 누르면 해당 옵션과 금액이 장바구니에 반영된다.
- 동일한 메뉴·옵션 조합을 두 번 담으면 수량은 2가 되고, 다른 옵션 조합은 별도 항목으로 보인다.
- 기본 가격 4,000원인 아메리카노(ICE)에 샷 추가(+500원)를 선택해 1개, 기본 가격 4,000원인 아메리카노(HOT)를 2개 담으면 항목 금액은 각각 4,500원과 8,000원, 총액은 12,500원으로 표시된다.
- 빈 장바구니에서는 주문 제출이 불가능하며, 주문 제출 중에는 중복 요청을 할 수 없다.
- 성공 시 성공 안내와 장바구니 초기화가 이루어지고, 실패 시 오류 안내와 기존 장바구니 유지가 이루어진다.
- 좁은 화면에서도 메뉴 정보, 옵션, 장바구니 총액 및 주요 버튼을 가로 스크롤 없이 이용할 수 있다.

### 4.8 미결정 사항
- 장바구니에서 수량을 변경하거나 항목을 삭제하는 기능은 와이어프레임에 표현되어 있지 않다. 구현 범위 확정 시 해당 기능의 필요 여부와 조작 방식을 결정한다.
- 주문 제출 후 보여줄 상세 확인 화면/정보와 주문 취소 가능 여부는 별도 주문 처리 요구사항에서 결정한다.

## 5. 관리자 화면 PRD

### 5.1 목표 및 사용자
- 관리자가 주문 건수와 메뉴별 재고를 확인하고, 재고를 조정하며, 접수된 주문을 처리할 수 있어야 한다.
- 이 화면은 매장의 주문 및 재고를 관리하는 운영자를 대상으로 한다.
- 기본 사항에 따라 인증 기능은 범위에서 제외한다.

### 5.2 화면 구성
1. **상단 내비게이션**
   - 브랜드명 `COZY`와 `주문하기`, `관리자` 메뉴를 표시한다.
   - `관리자`는 현재 화면임을 시각적으로 표시하고, `주문하기`는 주문 화면으로 이동한다.
2. **관리자 대시보드**
   - 총 주문 수, 주문 접수 수, 제조 중 수, 제조 완료 수를 요약해 표시한다.
   - 각 수치는 현재 주문 상태별 건수이며, 총 주문 수는 표시 대상인 전체 주문 건수다.
3. **재고 현황**
   - 메뉴별 카드에 메뉴명, 현재 재고 수량, 수량 증가(+) 및 감소(-) 버튼을 표시한다.
   - 재고 수량은 정수 단위로 표시한다.
4. **주문 현황**
   - 주문별 접수 시각, 주문 메뉴 및 수량, 주문 금액, 현재 처리 단계에 해당하는 동작을 표시한다.
   - 주문은 처음 `주문 접수` 상태로 표시한다. 관리자 동작은 현재 상태에 따라 `제조 시작` 또는 `완료`를 제공한다.
   - 주문이 없으면 주문이 없다는 빈 상태를 표시한다.

### 5.3 사용자 흐름 및 동작
1. 관리자가 화면에 진입하면 주문 상태별 건수, 메뉴별 재고, 처리할 주문 목록을 확인한다.
2. 재고 카드의 `+` 또는 `-` 버튼을 누르면 해당 메뉴 재고를 1개 증감하고 최신 수량을 표시한다.
3. 새 주문은 `주문 접수` 상태로 표시한다. 관리자가 `제조 시작`을 누르면 `제조 중`으로, 제조 중인 주문에서 `완료`를 누르면 `제조 완료`로 변경한다.
4. 주문 상태 변경에 성공하면 주문 목록과 대시보드 집계를 갱신한다. 실패하면 오류를 안내하고, 저장되지 않은 변경을 성공한 것처럼 표시하지 않는다.

### 5.4 기능 요구사항
- **대시보드 요약:** 주문 상태별 건수를 주문 데이터와 일치하게 표시한다. 상태 변경 후 관련 수치가 갱신되어야 한다.
- **재고 조회:** 관리 중인 커피 메뉴별 현재 재고를 표시한다.
- **재고 조정:** `+`는 수량을 1 증가시키고 `-`는 1 감소시킨다. 재고는 0 미만이 될 수 없으며 0일 때 감소 동작은 비활성화한다.
- **주문 조회:** 주문 시각, 메뉴명, 메뉴별 수량, 총 주문 금액 및 처리 상태를 식별할 수 있게 표시한다.
- **주문 상태 변경:** `주문 접수` 상태의 주문은 `제조 시작`으로 `제조 중` 상태로 변경할 수 있고, `제조 중` 주문은 `완료`로 `제조 완료` 상태로 변경할 수 있다. 처리 중에는 중복 입력을 막고, 성공하면 목록과 집계에 반영한다.
- **결과 안내:** 재고 변경 또는 주문 상태 변경이 실패하면 사용자가 오류를 알 수 있어야 하며, 재시도할 수 있도록 기존 표시를 보존하거나 서버의 최신 상태를 다시 불러온다.
- **화면 이동:** 상단 내비게이션에서 주문 화면과 관리자 화면을 오갈 수 있다.

### 5.5 예외 및 상태
- 주문, 재고 정보를 불러오는 중에는 로딩 상태를 표시한다. 불러오기에 실패하면 오류와 다시 시도할 방법을 제공한다.
- 메뉴가 없으면 재고 현황에 빈 상태를 표시한다.
- 재고 수량이 0인 메뉴는 0으로 표시하고 감소시킬 수 없다.
- 다른 요청으로 재고나 주문 상태가 먼저 변경되어 갱신 요청이 거부되면 최신 정보를 반영하고 결과를 사용자에게 알린다.
- 주문 상태 변경 요청이 실패해도 해당 주문 상태나 대시보드 건수를 임의로 변경하지 않는다.

### 5.6 레이아웃 및 접근성
- 대시보드, 재고 현황, 주문 현황을 구분된 영역으로 배치한다.
- 데스크톱에서는 재고 메뉴를 여러 열로 표시하며, 좁은 화면에서는 열 수를 줄여 가로 스크롤 없이 확인하고 조작할 수 있게 한다.
- 재고의 `+`, `-` 버튼은 어떤 메뉴의 수량을 변경하는지 보조 기술로도 식별할 수 있는 이름을 제공한다.
- 버튼은 키보드로 조작 가능해야 하며, 비활성화 상태와 주문 처리 결과를 색상만으로 전달하지 않는다.

### 5.7 인수 기준
- 대시보드의 총 주문 및 각 상태 건수가 실제 주문 목록의 상태별 건수와 일치한다.
- 재고가 10개인 메뉴에서 `+`를 한 번 누르면 11개, `-`를 한 번 누르면 9개로 표시된다.
- 재고가 0개일 때 감소시킬 수 없으며, 음수 재고가 표시되거나 저장되지 않는다.
- `주문 접수` 주문에서 `제조 시작`을 누르면 요청 성공 후 `제조 중` 상태와 대시보드 집계가 함께 갱신된다. 제조 중 주문에서 `완료`를 누르면 `제조 완료` 상태와 집계가 갱신된다.
- 재고 변경 또는 주문 상태 변경이 실패하면 오류 안내가 표시되고, 실패한 변경을 완료된 값으로 표시하지 않는다.
- 주문 및 재고가 없는 경우 각각 알아볼 수 있는 빈 상태가 표시된다.
- 좁은 화면에서도 주문 정보, 재고 수량, 주요 버튼을 가로 스크롤 없이 이용할 수 있다.

### 5.8 미결정 사항
- 주문 현황의 정렬 순서, 목록 페이지 처리, 완료 주문 보관/노출 방식은 별도 운영 정책에서 결정한다.

## 6. 백엔드 PRD

### 6.1 목표 및 범위
- PostgreSQL에 메뉴, 메뉴 옵션, 주문 및 주문 상세를 저장하고 관리한다.
- 프런트엔드가 메뉴 및 관리자 데이터를 조회하고, 주문 등록·재고 조정·주문 상태 변경을 수행할 수 있는 REST API를 제공한다.
- 사용자 인증과 결제 처리는 범위에 포함하지 않는다.
- API 요청 및 응답 본문은 JSON을 사용하고, 금액은 원 단위의 0 이상의 정수로 처리한다.

### 6.2 데이터 모델

#### Menus
| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | 정수 또는 UUID | 예 | 메뉴 식별자 |
| name | 문자열 | 예 | 커피 메뉴명 |
| description | 문자열 | 아니오 | 메뉴 설명 |
| price | 정수 | 예 | 기본 가격(원, 0 이상) |
| image_url | 문자열 | 아니오 | 메뉴 이미지 URL |
| stock_quantity | 정수 | 예 | 현재 재고 수량(0 이상) |
| created_at | 일시 | 예 | 생성 시각 |
| updated_at | 일시 | 예 | 마지막 수정 시각 |

#### Options
| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | 정수 또는 UUID | 예 | 옵션 식별자 |
| menu_id | Menus 식별자 | 예 | 이 옵션을 제공하는 메뉴 |
| name | 문자열 | 예 | 옵션명 |
| price | 정수 | 예 | 추가 가격(원, 0 이상) |
| created_at | 일시 | 예 | 생성 시각 |
| updated_at | 일시 | 예 | 마지막 수정 시각 |

각 옵션은 하나의 메뉴에 연결한다. 메뉴 또는 옵션이 기존 주문에서 참조 중일 때 주문 이력을 보존할 수 있도록 물리 삭제하지 않고 비활성화 또는 논리 삭제하는 정책을 사용한다.

#### Orders
| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | 정수 또는 UUID | 예 | 주문 식별자 |
| ordered_at | 일시 | 예 | 주문 접수 시각 |
| status | 문자열 | 예 | `received`, `preparing`, `completed` 중 하나 |
| total_amount | 정수 | 예 | 주문 총액(원) |
| created_at | 일시 | 예 | 생성 시각 |
| updated_at | 일시 | 예 | 마지막 수정 시각 |

한 주문에 여러 메뉴와 옵션 조합이 포함될 수 있으므로 주문 내역은 다음 상세 데이터로 저장한다.

#### OrderItems
| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | 정수 또는 UUID | 예 | 주문 상세 식별자 |
| order_id | Orders 식별자 | 예 | 소속 주문 |
| menu_id | Menus 식별자 | 예 | 주문한 메뉴 |
| menu_name | 문자열 | 예 | 주문 시점 메뉴명 스냅샷 |
| menu_price | 정수 | 예 | 주문 시점 기본 메뉴 가격 스냅샷(원) |
| quantity | 정수 | 예 | 주문 수량(1 이상) |
| unit_price | 정수 | 예 | 옵션을 포함한 주문 시점 단가(원) |
| line_amount | 정수 | 예 | 상세 금액(`unit_price × quantity`) |

#### OrderItemOptions
| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | 정수 또는 UUID | 예 | 주문 옵션 상세 식별자 |
| order_item_id | OrderItems 식별자 | 예 | 소속 주문 상세 |
| option_id | Options 식별자 | 아니오 | 원본 옵션 식별자 |
| option_name | 문자열 | 예 | 주문 시점 옵션명 스냅샷 |
| option_price | 정수 | 예 | 주문 시점 추가 금액 스냅샷(원) |

주문 당시 메뉴명, 메뉴 가격, 옵션명 및 옵션 가격을 상세 데이터에 보존한다. 메뉴나 옵션이 나중에 변경되어도 기존 주문 내역과 금액은 변하지 않아야 한다. 각 상세 단가는 `menu_price + 선택 옵션 가격 합계`로 계산하고, 주문 총액은 주문 상세 금액의 합과 일치해야 한다. 모든 외래 키와 수량·금액의 범위를 데이터베이스 제약 조건으로 보호한다.

### 6.3 데이터 흐름
1. 주문 화면 진입 시 프런트엔드는 메뉴 목록과 각 메뉴의 판매 옵션을 조회해 표시한다. 공개 메뉴 응답에는 재고 수량을 포함하지 않는다.
2. 관리자 화면 진입 시 메뉴 목록과 재고 수량, 주문 목록과 현재 상태를 조회해 대시보드·재고 현황·주문 현황을 표시한다.
3. 사용자가 메뉴와 옵션을 선택해 장바구니에 담는 동안 장바구니는 프런트엔드에서 관리한다. 동일 메뉴·동일 옵션 조합은 한 항목으로 수량을 합산한다.
4. 주문 제출 시 프런트엔드는 메뉴 ID, 수량, 옵션 ID를 서버에 전송한다. 서버는 현재 메뉴·옵션 가격과 재고를 다시 검증하고 총액을 계산한다. 클라이언트가 전송한 금액을 신뢰하지 않는다.
5. 주문 상세 생성과 재고 차감은 하나의 데이터베이스 트랜잭션으로 처리한다. 재고가 부족하거나 주문 생성 중 오류가 발생하면 전체 처리를 취소하고 일부 데이터만 변경하지 않는다. 동일 메뉴가 여러 상세 행에 있으면 수량을 합산해 재고를 검증하고 차감한다. 동시 주문에서도 재고가 음수가 되지 않도록 트랜잭션 안에서 재고를 잠그거나 조건부 원자 업데이트를 수행한다. 재고는 주문이 성공적으로 접수될 때 주문 수량만큼 차감한다.
6. 생성된 주문의 기본 상태는 `received`(화면 표시명: `주문 접수`)이다. 관리자는 `received → preparing → completed` 순서로 상태를 변경한다. 허용되지 않은 역방향 또는 단계 건너뛰기 전이는 거부한다.
7. 관리자가 재고 증감 또는 주문 상태 변경을 요청하면 서버 저장 성공 이후 최신 값을 화면에 반영한다. 요청 실패 시 기존 값을 유지하고 오류를 표시한다.

### 6.4 API 설계

#### 메뉴 목록 조회
- `GET /api/menus`
- 주문 화면용 판매 메뉴 목록과 각 메뉴의 옵션을 반환한다. 재고 수량은 포함하지 않는다.
- 성공 응답 예시:
  ```json
  {
    "items": [
      {
        "id": "menu-1",
        "name": "아메리카노 (ICE)",
        "description": "산뜻하고 깔끔한 밸런스",
        "price": 4000,
        "imageUrl": null,
        "options": [
          { "id": "option-1", "name": "샷 추가", "price": 500 },
          { "id": "option-2", "name": "시럽 추가", "price": 0 }
        ]
      }
    ]
  }
  ```

#### 관리자 메뉴·재고 목록 조회
- `GET /api/admin/menus`
- 메뉴명, 기본 가격, 이미지, 재고 수량 및 메뉴별 옵션을 반환한다.
- 메뉴가 없으면 `200 OK`와 빈 `items` 배열을 반환한다.

#### 메뉴 재고 조정
- `PATCH /api/admin/menus/{menuId}/stock`
- 요청 예시: `{ "adjustment": 1 }` 또는 `{ "adjustment": -1 }`
- `adjustment`는 `1` 또는 `-1`만 허용한다. 재고를 0 미만으로 변경하는 요청은 거부한다.
- 성공 시 갱신된 메뉴 ID와 재고 수량을 반환한다.

#### 주문 생성 및 재고 차감
- `POST /api/orders`
- 요청 예시:
  ```json
  {
    "items": [
      {
        "menuId": "menu-1",
        "quantity": 1,
        "optionIds": ["option-1"]
      },
      {
        "menuId": "menu-2",
        "quantity": 2,
        "optionIds": []
      }
    ]
  }
  ```
- 빈 주문, 1 미만 수량, 존재하지 않거나 해당 메뉴에 속하지 않는 옵션, 판매할 수 없는 메뉴, 재고 부족 요청은 거부한다.
- 서버는 현재 저장된 가격으로 단가·상세 금액·총액을 계산하고, 주문 상세와 옵션 스냅샷을 기록한다.
- 주문 생성과 메뉴별 재고 차감을 하나의 트랜잭션으로 수행한다.
- 성공 시 `201 Created`와 생성된 주문 ID, 주문 시각, 상태, 서버 계산 총액 및 상세 내역을 반환한다.
- 성공 응답 예시:
  ```json
  {
    "id": "order-1",
    "orderedAt": "2026-10-15T01:30:00.000Z",
    "status": "received",
    "totalAmount": 12500,
    "items": [
      {
        "menuId": "menu-1",
        "menuName": "아메리카노 (ICE)",
        "quantity": 1,
        "options": [
          { "optionId": "option-1", "name": "샷 추가", "price": 500 }
        ],
        "unitPrice": 4500,
        "lineAmount": 4500
      },
      {
        "menuId": "menu-2",
        "menuName": "아메리카노 (HOT)",
        "quantity": 2,
        "options": [],
        "unitPrice": 4000,
        "lineAmount": 8000
      }
    ]
  }
  ```

#### 주문 단건 조회
- `GET /api/orders/{orderId}`
- 주문 ID에 해당하는 주문의 시각, 상태, 상세 메뉴·수량·옵션, 상세 금액 및 총액을 반환한다.
- 주문이 없으면 `404 Not Found`를 반환한다.

#### 관리자 주문 목록 조회
- `GET /api/admin/orders`
- 주문 시각 내림차순으로 주문과 상세 내역을 반환한다. 상태별 집계에 필요한 모든 상태를 포함하며, 정렬·페이지 처리 정책은 추후 확정한다.

#### 주문 상태 변경
- `PATCH /api/admin/orders/{orderId}/status`
- 요청 예시: `{ "status": "preparing" }` 또는 `{ "status": "completed" }`
- 허용 전이는 `received → preparing`, `preparing → completed`뿐이다. 이미 완료된 주문, 허용되지 않은 상태 전이 또는 존재하지 않는 주문은 갱신하지 않는다.
- 성공 시 갱신된 주문 상태와 변경 시각을 반환한다.

### 6.5 공통 응답 및 오류 처리
- 성공한 조회·수정은 `200 OK`, 주문 생성은 `201 Created`를 사용한다.
- 잘못된 요청 형식 또는 허용되지 않는 상태 전이는 `400 Bad Request`, 존재하지 않는 리소스는 `404 Not Found`, 재고 부족 또는 동시 수정 충돌은 `409 Conflict`, 서버 내부 오류는 `500 Internal Server Error`로 응답한다.
- 오류 응답은 다음 공통 형식을 사용한다.
  ```json
  {
    "error": {
      "code": "INSUFFICIENT_STOCK",
      "message": "요청한 메뉴의 재고가 부족합니다."
    }
  }
  ```
- 오류가 발생해도 실패한 주문·재고·상태 변경이 저장되지 않아야 한다. 프런트엔드는 오류를 사용자에게 알리고 저장된 것처럼 값을 갱신하지 않는다.

### 6.6 백엔드 인수 기준
- `GET /api/menus`는 메뉴와 메뉴별 옵션을 반환하고 공개 응답에서 재고 수량을 제외한다. `GET /api/admin/menus`는 재고 수량을 포함한다.
- 유효한 주문 생성 요청은 서버가 계산한 주문 상세와 총액으로 저장되며 기본 상태는 `received`이다.
- 주문 생성 성공 시 주문 내역 기록과 메뉴 재고 차감이 모두 반영되고, 어느 한쪽이라도 실패하면 둘 다 반영되지 않는다.
- 재고가 주문 수량보다 부족하면 `409 Conflict`를 반환하고 주문을 생성하거나 재고를 변경하지 않는다.
- 주문 ID 조회는 해당 주문의 시각, 상태, 메뉴·수량·옵션 및 금액을 반환하며 미존재 ID는 `404 Not Found`를 반환한다.
- 관리자 상태 변경은 `received → preparing → completed` 전이만 허용하고, 변경 결과는 주문 목록 및 상태별 집계와 일치한다.
- 재고 수량은 음수가 될 수 없고 관리자 증감 API는 한 번에 1개씩만 변경한다.
